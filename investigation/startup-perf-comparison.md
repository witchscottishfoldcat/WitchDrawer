# 启动性能优化：修复前后对比

测量工具：`tools/StartupPerf/run.sh`（绕过沙箱 NuGet 限制，直接 csc 编译运行）。
场景：20 盒 × 30 项（共 600 文件项）+ 232 项设置，再次启动；另测空目录首次启动。
同一台机器、同一数据规模下先后测量；原始输出见 `startup-perf-baseline.txt` 与 `startup-perf-after.txt`。

## 结果

| 指标 | 修复前 | 修复后 | 变化 |
| --- | --- | --- | --- |
| `InitializeAsync`（再次启动，含恢复扫描/路径修复/默认盒子） | 73 ms | 42 ms | -42% |
| `InitializeAsync`（首次启动，空目录） | 89 ms | 84 ms | 基本持平 |
| 启动设置读取（232 项） | 232 次查询 / 504 ms | 1 次查询 / 3 ms | 查询数 -99.6%，耗时 -99% |
| 上述工作的线程位置 | 部分在界面线程同步完成（SQLite 异步 API 会同步完成） | 全部在后台线程 | 界面线程阻塞 ≈ 0 |

## 说明

- 路径修复改为“先比较记录路径，再决定是否做文件存在检查”：再次启动的常态是路径全部一致，
  每个文件项的存在检查（600 次 `File.Exists`/`Directory.Exists`）被跳过，这是 73→42 ms 的主要来源。
- 设置快照把“每盒 11 项 + 全局 12 项”的逐键读取（每键独立打开一次连接）合并为一次连接一条查询，
  主窗口与桌面盒子共享同一快照；快照仅限本轮启动，运行期间读取仍走实时查询，写入照常持久化。
- 桌面盒子首次刷新只剩 `App.OnStartup` 里一个入口；`MainViewModel.LoadAsync` 触发的
  `BoxesChanged` 在启动首刷完成前被守卫跳过，运行期间新增/删除盒子的刷新事件与串行保护不变。
- 快捷面板不再随启动全量预加载：首次打开时 `EnsureLoadedAsync` 完整加载一次，
  之后继续走增量刷新；未初始化期间的文件变更不触发扫描，首次打开不会遗漏。
- 启动计时埋点（`StartupTimer`）与界面线程卡顿监控（`UiThreadStallMonitor`）写入应用日志：
  每阶段的增量/累计耗时、超过 150 ms 的界面线程阻塞都会记录，可用于真实环境的
  “窗口出现慢 / 出现后操作卡”归因与后续对比。

## 界面帧预算

启动期磁盘操作（数据库初始化、恢复日志、路径修复、设置读取、快捷面板数据）均已移出界面线程；
窗口创建、绑定、主题应用仍在界面线程（WPF 要求）。8.33 ms 帧预算内不再安排启动期 IO。
真实机器上的分阶段耗时以日志中 `[startup]` 行（含 UI stall 记录）为准。
